The 4-Step Transition: Requirements to Architecture

How to use math and data requirements to systematically drive the DSL and architectural decisions

Interview Playbook
Step 1 FRs → Invariants

FR → Commands & Events

Map each functional capability directly to an Actor -> Command() and its resulting immutable facts [Events].

user -> makeRequest()
 -> [request-logged]
Step 2 NFR Math → Scale

Math → DCB Boundaries

Use QPS and concurrency numbers to justify concurrency boundaries without global locks.

50k QPS → Partition
 [$user, $window]
Step 3 SLA → Sizing

Latency → View & Storage

Use P99 latency (<2ms) and data footprint math (640MB) to separate hot in-memory views from cold logs.

view Quota @bergcache
 (RAM: 640MB, O(1))
Step 4 Resilience → Sagas

Availability → Policies

Offload secondary NFRs (WAF blocking, metrics, fraud alerts) onto async event-driven sagas.

rate-limit-exceeded
 -> waf-bot -> block()

Actors

Declare who interacts with your system. Makes the "who can do what" question impossible to ignore.

Step 0 
actor User { auth: session, tier: free|pro }
actor Admin { auth: oauth, mfa: required }
actor Visitor { auth: none }
Why Surface auth & permissions

Without actors, commands like user -> makeRequest() hide authentication, authorization, and abuse patterns. Declaring actors makes these visible.

Attributes auth, tier, scope, rateLimit

Each actor declares authentication method, access tier, permission scope, and implicit rate limits. This drives guard logic and boundary design.

In Interviews Signal full-system thinking

Opening with actors shows you're thinking about the full system: not just the happy path, but who can trigger it, what they can do, and what abuse looks like.

System Context

Declare external dependencies, SLAs, regions, and data classification. The "why" behind the numbers.

Step 0 
system RateLimiterAPI {
  external: stripe (payment-gateway), sentry (monitoring)
  slo: 99.99% uptime, p99 < 2ms
  region: us-primary, eu-secondary
  data-classification: pii
}
Why Ground the numbers

@cost(writeRpsPeak=50000) is arbitrary without context. System context explains where the number comes from and what constraints drive it.

External Deps Every dep is a failure point

Each external declaration implies a failure mode. If Stripe is down, what happens to processPayment? The system context forces you to model that.

In Interviews Set the constraints

Open with the system context so the interviewer knows the constraints you're working within. This signals you think about the full system, not just the happy path.

Thinking Guide

The question vocabulary for inspecting designs. Use this to find what's missing.

When you see...

actor -> command()

Ask: Who else could be this actor? What permissions do they have? What happens if they're not authenticated?

When you see...

boundary ... @cost(writeRpsPeak=X)

Ask: What's the failure mode if we exceed X? What's the recovery strategy?

When you see...

from [View(...) @eventual]

Ask: What's the maximum staleness the business can tolerate? What breaks if the view is 5 minutes old?

When you see...

policy ... -> external-svc

Ask: What happens if external-svc is down? Do we retry? Fallback? Fail?

When you see...

--[guard]--> with complex logic

Ask: Is this guard evaluated in the hot path? Can it be cached? What's the latency budget?

When you see...

Multiple actors in the same boundary

Ask: Do they share a partition key? Could one actor's traffic starve another's?

Full Event Modeling Slice Coverage

How this DSL maps to the 4 canonical slice patterns from Event Modeling

1. State Change Slice Blue → Orange
UI → Command → Event

User or caller submits a command. Pure decider checks past facts and appends new domain event. 

customer -> registerUser(email, hash) on [user-registered*]
  --[emailNotTaken]--> [
    user-registered { userId, email, hash }
  ]
2. State View Slice Orange → Green
Events → Projection → Screen

Domain facts projected into a read model / view queried by the client or API. 

view UserProfileView(userId) = [
  user-registered, profile-updated*
] => { email, name, avatarUrl } @bergcache(ttl=1h)
3. Automation Slice Orange → Purple → Blue
Event → Policy → Command

An event triggers an automated process / policy that issues a subsequent command to another slice. 

user-registered { userId, email }
  -> welcome-worker -> sendWelcomeEmail(userId, email)
4. Translation / Integration External ↔ Domain
Inbound & Outbound Adapters

Inbound webhooks/polls translated into domain commands, or outbound domain events pushing to external APIs. 

// Inbound Webhook Adapter
stripe-webhook -> ingestStripeCharge(chargePayload) -> [
  payment-captured { invoiceId, stripeId, amount }
]

The Decider & Projection Flow

How commands, facts, DCB query boundaries, projections, and policies connect

End-to-End Flow

The 4 Grammar Primitives

Every system design requirement can be mapped to one of these four components.

1. Command (Decider / Write) Actor -> Command on [Events] from [Views] -> [Events]

Represents an intention to change state. Pure decider evaluates given facts and guards to emit zero or more new immutable events. 

user -> transferFunds(toUser, amount)
on [account-opened(fromUser), funds-deposited*(fromUser)]
from [AccountBalance(fromUser) as balance]
  --[balance.currentBalance >= amount]--> [
    funds-transferred { fromUser, toUser, amount }
  ]
  --[default]--> [ transfer-rejected { reason: "insufficient_funds" } ]
2. View (Projection / Query) view Name = [Events] -> { State }

Deterministic read-model projection aggregated from domain facts. Annotated with storage layer, key format, and caching strategy. 

view AccountBalance(userId) = [funds-transferred*, funds-deposited*] -> {
  currentBalance,
  lastTransactionAt,
  status
} @bergcache(key="balance:{userId}", ttl=15m)
3. Policy (Reactor / Saga) event {payload} --[Guard]--> worker -> Command()

Event-driven automations. When an event occurs, an asynchronous worker or service executes a subsequent command. 

funds-transferred { fromUser, toUser, amount }
  --[amount > 10000]--> fraud-service -> flagSuspiciousTransfer(fromUser, amount)
funds-transferred
  -> notification-worker -> sendReceipt(toUser)
4. Boundary (DCB Tags & Sharding) boundary Name(key) @partition(shardKey="...")

Dynamic Consistency Boundaries (DCB). Specifies metadata tags used to load fact streams and partition data without rigid aggregates. 

boundary TenantAccountBoundary(tenantId, userId)
  @partition(shardKey="tenantId")
  @owner("accounting-svc")
  @replication(mode="async", lag_sla="<2s")

Architecture is inferred, not bolted on

Same primitives, different view

This language does not need a separate "architecture" grammar to be useful. The same model tells you architecture when you add annotations like @bergcache, @partition, @time, @confidence, @cost, and @ops. Those declarations reveal read path behavior, trust boundary, certainty level, resource envelope, and operating ownership without bloating the core syntax.

Rate Limiter Specification (Refined)

Your original design transformed into complete interview-ready DSL

Sliding Window Token Bucket
DSL Specification
// 1. AUTHENTICATION DECIDER
user -> authenticate(username, password)
on [user-created(email)]
  --[credentialsValid]--> [ user-authenticated { userId, tierId } ]
// 2. RATE LIMITER DECIDER (DCB Boundary: $user + $window)
user -> makeRequest(resourceId, data)
on [
  user-authenticated(userId),
  request-logged*(userId, window: currentMinute)
]
from [UserTierCache(userId) @fresh<24h> as tier]
  --[count(request-logged) < tier.limit]--> [
    request-logged { userId, resourceId, requestMinute, requestAt: clock.wall() }
  ]
  --[count(request-logged) >= tier.limit]--> [
    rate-limit-exceeded { userId, resourceId, retryAfter: window.end(currentMinute,1m)-clock.wall() }
  ]
// 3. FAST-PATH CACHE PROJECTION
view UserQuota(userId) = [tier-assigned*(userId), request-logged*(userId)] -> {
  tier, limit, remaining, resetAt
} @bergcache(key="quota:{userId}", ttl=60s) @cost(memory="~6MB/region")
// 4. SECURITY ABUSE POLICY
rate-limit-exceeded { userId }
  --[scoreBy("quota-anomaly-v2", userId) > 0.7]--> waf-bot -> applyTemporaryBan(userId, duration=15m)
What this signals in interview
Consistency Dynamic Boundary

You explicitly bounded concurrency to $user and currentMinute. No global database lock or monolithic aggregate root needed.

Architecture Inferred from metadata

The same model implies architecture: @bergcache suggests read optimization, @partition suggests sharding, and @owner/@service describe service boundaries without inventing a second language.

Performance Read/Write Separation

The decider defines the authoritative write path, while the UserQuota view gives an O(1) in-memory cache read path via Bergcache.

Extensibility Zero Coupling

WAF abuse defense is hooked up purely via an asynchronous reactor policy on rate-limit-exceeded without touching the request handler.

High Read / Write Scale

Order Checkout & Payment Saga

Distributed Consistency 
customer -> placeOrder(cartId, items, paymentMethod) -> [
  order-placed { orderId, customerId, items, totalAmount }
]
order-placed -> inventory-svc -> reserveStock(orderId, items) on [stock-counted*(skuId)]
  --[inStock]--> [ stock-reserved { orderId } ]
  --[outOfStock]--> [ stock-reservation-failed { orderId, reason } ]
stock-reserved -> payment-svc -> chargeCard(orderId, totalAmount)
  --[chargeSuccess]--> [ payment-captured { orderId, txnId } ]
  --[chargeFailed]--> [ payment-failed { orderId, error } ]
// Compensating transaction
payment-failed -> inventory-svc -> releaseStock(orderId) -> [
  stock-released { orderId }
]
